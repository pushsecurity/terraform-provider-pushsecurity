# pushsecurity_password_logging_prevention (Resource)

Manages the password logging prevention control: whether entering a company password into a non-login field is monitored or blocked.

~> This resource owns the whole `passwordLoggingPrevention` configuration. The API replaces the entire document on every write, so this control is either managed by Terraform or managed in the console — not both. Import the existing configuration before your first apply.

Destroying this resource does not remove the control, which cannot be removed. It writes an empty configuration: no rules, and default control-wide settings.

## Example usage

```terraform
resource "pushsecurity_password_logging_prevention" "this" {
  rules = [
    {
      key     = "block-on-unapproved"
      name    = "Block company passwords on unapproved apps"
      enabled = true
      mode    = "BLOCK"
      # title and subtext are required for BLOCK and rejected for every other
      # mode, so the MONITOR rule below must not set them.
      title   = "Do not use your company password here"
      subtext = "This app is not approved for company credentials."

      criteria = {
        approval_statuses = { matches = ["NOT_APPROVED", "UNDER_REVIEW"] }
      }
    },
    {
      key     = "monitor-everything-else"
      name    = "Monitor everywhere else"
      enabled = true
      mode    = "MONITOR"
    },
  ]
}
```

### Nested Schema for `rules`

Required:

- `enabled` (Boolean) Whether the rule is active.
- `mode` (String) What happens when the rule matches. One of `OFF`, `MONITOR` or `BLOCK`.
- `name` (String) A short name to help you recognise the rule. Not required to be unique. At most 250 characters.

Optional:

- `criteria` (Attributes) Restricts the rule to apply only under these conditions. A rule with no criteria applies to everyone. (see [below for nested schema](#nestedatt--rules--criteria))
- `key` (String) A stable identifier for this rule, chosen by you and unique within the control. It is never sent to the API; the provider uses it to remember which server-side rule this configuration block corresponds to.

~> Set this on every rule. Rule names are not unique — the console generates names from a template, so duplicates are common — and without `key` the provider has to match rules by position. Reordering positionally matched rules keeps the server-side rule identifiers but moves them onto different rules. Nothing in Push refers to a rule identifier, so the tenant behaves the same either way; set a key if your own tooling reads the identifiers the API returns.
- `subtext` (String) Message shown to the user when password entry is blocked. Markdown is supported. At most 1000 characters.
- `title` (String) Heading shown to the user when password entry is blocked. At most 75 characters. Must not contain `&`, `<` or `>`, which the API stores HTML-escaped.

Read-Only:

- `id` (String) The rule's server-assigned identifier.

## Import

With Terraform 1.14 or later, `terraform query -generate-config-out` writes
the resource and its import block for you, using the `pushsecurity_password_logging_prevention` list
resource. Its page shows how.

Import the existing configuration before your first apply, so that the apply is
a no-op rather than a replacement of whatever is already live.

```terraform
import {
  to       = pushsecurity_password_logging_prevention.this
  provider = pushsecurity
  id       = "default"
}
```

Terraform 1.12 and later also accept the resource's identity in place of `id`.
The value is ignored, as the identifier is:

```terraform
import {
  to       = pushsecurity_password_logging_prevention.this
  provider = pushsecurity
  identity = { id = "default" }
}
```

Either way, let Terraform write the configuration:

```shell
terraform plan -generate-config-out=generated.tf
```

Move the generated resource into your configuration, then **remove the
`provider` argument from the import block** — Terraform only accepts it on
import blocks that generate configuration, and leaving it in place fails the
next plan. Then run `terraform apply` to record the import.

Two things to expect:

- Generated rules have `key = null`, because keys are provider-side only and
  cannot be recovered from the API. Fill them in while adopting the control;
  the first apply after doing so is a no-op on the API.
- The API can return configuration that it rejects on write, so an import can
  produce a zero-diff plan and still fail validation on a later apply. This
  provider checks the API's cross-field rules during plan, so such rules are
  reported against the offending attribute before anything is
  written. Fix them as part of adoption.
