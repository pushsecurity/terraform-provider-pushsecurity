# pushsecurity_clipboard_blocking (Resource)

Manages the clipboard blocking control: which copy and paste operations are monitored, warned on or blocked, and whether their content is captured.

~> This resource owns the whole `clipboardBlocking` configuration. The API replaces the entire document on every write, so this control is either managed by Terraform or managed in the console — not both. Import the existing configuration before your first apply.

Destroying this resource does not remove the control, which cannot be removed. It writes an empty configuration: no rules, and default control-wide settings.

## Example usage

```terraform
resource "pushsecurity_clipboard_blocking" "this" {
  globals = {
    # `enum` is derived by the server from `name`, and is what rules reference
    # in criteria.regex_patterns.
    custom_content_patterns = [
      { name = "Incident ticket", regex = "INC-\\d{6}" },
    ]
  }

  rules = [
    {
      key             = "block-ticket-copy"
      name            = "Block copying incident references"
      enabled         = true
      mode            = "BLOCK"
      operation       = "COPY"
      content_capture = true
      mask_pii        = true # required whenever content_capture is true
      title           = "Copy blocked"
      subtext         = "Incident references may not be copied off-platform."

      # Required because this rule matches regex patterns. A BLOCK rule that
      # matched no regex patterns would need acknowledge_button_text instead.
      copy_redacted_button_text = "Copy redacted"

      criteria = {
        regex_patterns = { matches = ["CUSTOM_INCIDENT_TICKET"] }
      }
    },
    {
      key             = "monitor-external-pastes"
      name            = "Monitor pastes into external sites"
      enabled         = true
      mode            = "MONITOR"
      operation       = "PASTE"
      content_capture = false

      # criteria is required on this control, and must match on at least one of
      # url_patterns or regex_patterns.
      criteria = {
        url_patterns = { matches = ["*://*.example.com/*"] }
      }
    },
  ]
}
```

### Nested Schema for `rules`

Required:

- `content_capture` (Boolean) Whether the matching clipboard content is captured on the resulting events.
- `criteria` (Attributes) Restricts the rule to apply only under these conditions. (see [below for nested schema](#nestedatt--rules--criteria))
- `enabled` (Boolean) Whether the rule is active.
- `mode` (String) What happens when the rule matches. One of `OFF`, `MONITOR`, `WARN` or `BLOCK`.
- `name` (String) A short name to help you recognise the rule. Not required to be unique. At most 250 characters.
- `operation` (String) Which clipboard operation the rule applies to. One of `COPY` or `PASTE`.

Optional:

- `acknowledge_button_text` (String) Text of the banner button that dismisses the banner. At most 75 characters. Must not contain `&`, `<` or `>`, which the API stores HTML-escaped.
- `copy_original_button_text` (String) Text of the banner button that proceeds with the original content. At most 75 characters. Must not contain `&`, `<` or `>`, which the API stores HTML-escaped.
- `copy_redacted_button_text` (String) Text of the banner button that copies a redacted version of the content. At most 75 characters. Must not contain `&`, `<` or `>`, which the API stores HTML-escaped.
- `key` (String) A stable identifier for this rule, chosen by you and unique within the control. It is never sent to the API; the provider uses it to remember which server-side rule this configuration block corresponds to.

~> Set this on every rule. Rule names are not unique — the console generates names from a template, so duplicates are common — and without `key` the provider has to match rules by position. Reordering positionally matched rules keeps the server-side rule identifiers but moves them onto different rules. Nothing in Push refers to a rule identifier, so the tenant behaves the same either way; set a key if your own tooling reads the identifiers the API returns.
- `mask_pii` (Boolean) Whether personally identifiable information is masked in captured content. Required when `content_capture` is true, and must be omitted when it is false: the API drops it.
- `subtext` (String) Message of the banner shown to the user. Markdown is supported. At most 1000 characters.
- `title` (String) Heading of the banner shown to the user. At most 75 characters. Must not contain `&`, `<` or `>`, which the API stores HTML-escaped.

Read-Only:

- `id` (String) The rule's server-assigned identifier.

## Import

With Terraform 1.14 or later, `terraform query -generate-config-out` writes
the resource and its import block for you, using the `pushsecurity_clipboard_blocking` list
resource. Its page shows how.

Import the existing configuration before your first apply, so that the apply is
a no-op rather than a replacement of whatever is already live.

```terraform
import {
  to       = pushsecurity_clipboard_blocking.this
  provider = pushsecurity
  id       = "default"
}
```

Terraform 1.12 and later also accept the resource's identity in place of `id`.
The value is ignored, as the identifier is:

```terraform
import {
  to       = pushsecurity_clipboard_blocking.this
  provider = pushsecurity
  identity = { id = "default" }
}
```

Either way, let Terraform write the configuration:

```shell
terraform plan -generate-config-out=generated.tf
```

Move the generated resource into your configuration, then **remove the
`provider` argument from the import block** — Terraform only accepts it on
import blocks that generate configuration, and leaving it in place fails the
next plan. Then run `terraform apply` to record the import.

Two things to expect:

- Generated rules have `key = null`, because keys are provider-side only and
  cannot be recovered from the API. Fill them in while adopting the control;
  the first apply after doing so is a no-op on the API.
- The API can return configuration that it rejects on write, so an import can
  produce a zero-diff plan and still fail validation on a later apply. This
  provider checks the API's cross-field rules during plan, so such rules are
  reported against the offending attribute before anything is
  written. Fix them as part of adoption.
