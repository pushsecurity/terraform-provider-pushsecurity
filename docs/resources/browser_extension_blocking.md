# pushsecurity_browser_extension_blocking (Resource)

Manages the browser extension blocking control: which browser extensions employees may install and run.

~> This resource owns the whole `browserExtensionBlocking` configuration. The API replaces the entire document on every write, so this control is either managed by Terraform or managed in the console — not both. Import the existing configuration before your first apply.

Destroying this resource does not remove the control, which cannot be removed. It writes an empty configuration: no rules, and default control-wide settings.

## Example usage

```terraform
resource "pushsecurity_browser_extension_blocking" "this" {
  rules = [
    {
      key     = "allow-approved-extensions"
      name    = "Allow the extensions we have reviewed"
      enabled = true
      mode    = "ENABLE"

      criteria = {
        browser_extensions = {
          matches = ["aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa", "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"]
        }
      }
    },
    {
      key     = "block-sideloaded"
      name    = "Block sideloaded and development extensions"
      enabled = true
      mode    = "BLOCK"
      title   = "This extension is blocked"
      subtext = "Extensions installed outside the store are not permitted."

      criteria = {
        browser_extension_deployment_type = { matches = ["SIDELOAD", "DEVELOPMENT"] }
        browser_extension_profile         = { matches = ["COMPANY_DOMAINS"] }
      }
    },
    {
      key     = "block-broad-permissions"
      name    = "Block extensions that can read every page"
      enabled = true
      mode    = "BLOCK"
      title   = "This extension asks for too much"
      subtext = "It can read and change data on every site you visit."

      criteria = {
        browser_extension_permissions = { matches = ["<all_urls>", "tabs"] }
        employee_groups               = { matches = ["Security"], action = "EXCLUDE" }
      }
    },
  ]
}
```

Required:

Optional:

- `key` (String) A stable identifier for this rule, chosen by you and unique within the control. It is never sent to the API; the provider uses it to remember which server-side rule this configuration block corresponds to.

~> Set this on every rule. Rule names are not unique — the console generates names from a template, so duplicates are common — and without `key` the provider has to match rules by position. Reordering positionally matched rules keeps the server-side rule identifiers but moves them onto different rules. Nothing in Push refers to a rule identifier, so the tenant behaves the same either way; set a key if your own tooling reads the identifiers the API returns.

- `title` (String) Heading shown to the user when an extension is blocked. At most 75 characters. Must not contain `&`, `<` or `>`, which the API stores HTML-escaped.

## Import

Import the existing configuration before your first apply, so that the apply is
a no-op rather than a replacement of whatever is already live.

```terraform
import {
  to       = pushsecurity_browser_extension_blocking.this
  provider = pushsecurity
  id       = "default"
}
```

```shell
terraform plan -generate-config-out=generated.tf
```

Move the generated resource into your configuration, then **remove the
`provider` argument from the import block** — Terraform only accepts it on
import blocks that generate configuration, and leaving it in place fails the
next plan. Then run `terraform apply` to record the import.

Two things to expect:

- Generated rules have `key = null`, because keys are provider-side only and
  cannot be recovered from the API. Fill them in while adopting the control;
  the first apply after doing so is a no-op on the API.
- The API can return configuration that it rejects on write, so an import can
  produce a zero-diff plan and still fail validation on a later apply. This
  provider checks the API's cross-field rules during plan, so such rules are
  reported against the offending attribute before anything is
  written. Fix them as part of adoption.
