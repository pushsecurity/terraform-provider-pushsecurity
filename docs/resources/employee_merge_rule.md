# pushsecurity_employee_merge_rule (Resource)

Merges employees by the shape of their addresses rather than by naming them: wherever an employee has a second address matching one of `patterns`, it is merged into them.

```terraform
resource "pushsecurity_employee_merge_rule" "admin_aliases" {
  patterns = ["{local}.admin@{domain}", "{local}.support@{domain}"]
}
```

A pattern is filled in from each employee's own address — `{local}` and `{domain}` — and the result is looked for in the tenant. Matching in that direction is what lets a match say whose address it is, which a wildcard could not.

~> **Terraform does not undo a merge**, and an address that had no accounts cannot be split out again at all, so a mistaken pattern cannot always be put right. `max_merges` caps one apply, `pending_merges` shows exactly which pairs the apply will merge, and destroying the rule leaves everything it merged merged.

Employees whose own address matches a pattern are never treated as a primary, so aliases do not chain. An address that two people could claim is reported as an error rather than merged into one of them.

## Example usage

```terraform
# The same merge, expressed as a shape rather than as a list of people:
# wherever somebody has a .admin or .support address, it belongs to them.
#
# {local} and {domain} are filled in from each employee's own address, so a
# match knows whose address it is. New aliases are merged by the plan that
# follows them, with nobody editing this file.
resource "pushsecurity_employee_merge_rule" "admin_aliases" {
  patterns = [
    "{local}.admin@{domain}",
    "{local}.support@{domain}",
  ]

  # Only people in the corporate domain are treated as owners of an alias.
  domains = ["example.com"]

  # Shared mailboxes that happen to follow the same naming convention.
  exclude_emails = ["security.admin@example.com"]

  # A merge can be undone only in part, so an apply that would merge more than
  # this fails and shows the pairs instead. Raise it deliberately, once.
  max_merges = 10
}
```

## How matching works

Each pattern is filled in from an employee's own address — `{local}` and
`{domain}` — and the result is looked for in the tenant. Matching in that
direction, rather than testing every address against a wildcard, is what lets a
match say *whose* address it is: `ada.lovelace.admin@example.com` is only a
merge candidate because `ada.lovelace@example.com` exists.

Two cases are deliberately refused rather than guessed:

- **Aliases do not chain.** An employee whose own address matches a pattern is
  never treated as an owner, so `a.admin@` does not acquire `a.admin.admin@` in
  the same apply that merges it into `a@`.
- **An address two people could claim is an error.** The plan fails naming both,
  and the address is left alone until a `pushsecurity_employee_merge` resource or
  `exclude_emails` settles it.

## Reviewing what a rule will do

A rule's effects are not written down in the configuration, so they are put in
the plan instead. `merged` holds every pair the rule has merged, as
`secondary -> primary`, and the pairs the apply is about to add appear as
additions:

```text
  ~ resource "pushsecurity_employee_merge_rule" "admin_aliases" {
      ~ merged = [
          + "ada.lovelace.admin@example.com -> ada.lovelace@example.com",
        ]
    }
```

`max_merges` bounds one apply. A rule that suddenly matches far more than
expected — a pattern typo, a new domain arriving in the tenant — fails the plan
and lists the pairs rather than merging them, because Terraform does not undo a
merge, and an address that had no accounts cannot be split out again at all.

`pending_merges` is what makes a returning address a change at all: a refresh
puts it there, and the plan empties it again.

## Aliases and `pushsecurity_employee` do not mix

A merged address stops existing as an employee. A `pushsecurity_employee` resource that
manages one will therefore propose to create it again on the next plan, and this
rule will merge it again on the apply after that — a loop that consumes a licence
each time round. Manage people with `pushsecurity_employee`; leave their aliases to the
rule.

## Schema

### Required

- `patterns` (Set of String) The address shapes to merge, written with the placeholders `{local}` and `{domain}`: `{local}.admin@{domain}`, `{local}+svc@{domain}`, `{local}@admin.{domain}`. At least one placeholder is required — a pattern without one names a single fixed address, which is what `pushsecurity_employee_merge` is for.

### Optional

- `domains` (Set of String) Only consider employees whose own address is in one of these domains as a primary. Unset means every domain the tenant holds, which on a tenant with contractor or test domains is rarely what is wanted.
- `exclude_emails` (Set of String) Addresses this rule never touches, on either side of a pair. Shared mailboxes that follow the same naming convention as a person's alias belong here.
- `max_merges` (Number) The most merges one apply may perform. Defaults to 25. A plan that would exceed it fails, naming the count: a pattern that matches far more than expected is the one mistake this resource cannot walk back.

### Read-Only

- `merged` (Set of String) Every pair this rule has merged, as `secondary -> primary`, and the pairs the next apply will add — which is how a plan shows who a rule is about to merge before it does it.

It only grows. It records what the provider did: a merged address leaves no separate employee behind, so the tenant cannot confirm it afterwards.
- `pending_merges` (Set of String) The pairs the next apply will merge, as `secondary -> primary`, refreshed from the tenant on every plan. Empty when the tenant already satisfies the rule.

## Not importable

There is nothing to import: a rule is a statement about shapes, and the merges
it has performed are not recorded anywhere the API exposes. Adopting a tenant
that was merged by hand means writing the rule and letting the first plan show
whatever is left outstanding — which, for addresses already merged, is nothing.
