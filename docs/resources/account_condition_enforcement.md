# pushsecurity_account_condition_enforcement (Resource)

Manages the account condition enforcement control: whether logins to selected apps are monitored, warned on or blocked, depending on the email domain the user logs in with, how they log in and the browser they use. A `WARN` rule shows a page the user can continue past or end the session from; a `BLOCK` rule shows one from which they can only end it, which signs them out of the app.

~> This resource owns the whole `accountConditionEnforcement` configuration. The API replaces the entire document on every write, so this control is either managed by Terraform or managed in the console — not both. Import the existing configuration before your first apply.

Destroying this resource does not remove the control, which cannot be removed. It writes an empty configuration: no rules, and default control-wide settings.

## Example usage

```terraform
resource "pushsecurity_account_condition_enforcement" "this" {
  rules = [
    {
      key     = "block-personal-ai-logins"
      name    = "Block password logins to AI apps with a personal email"
      enabled = true
      mode    = "BLOCK"
      # BLOCK requires these three, and rejects continue_button_text.
      title                 = "Use your work account"
      subtext               = "Sign in to this app with your company email address."
      terminate_button_text = "Sign out"

      criteria = {
        # app_types and domain_scope are required on every rule.
        app_types    = { matches = ["OPENAI_CHATGPT", "ANTHROPIC_CLAUDE", "GOOGLE_GEMINI"] }
        domain_scope = "SPECIFIC_DOMAINS"
        # Required when domain_scope is SPECIFIC_DOMAINS, rejected otherwise.
        login_domains = { matches = ["gmail.com", "outlook.com"] }
        login_types   = { matches = ["PASSWORD_LOGIN"] }
      }
    },
    {
      key                   = "warn-non-company-logins"
      name                  = "Warn on code hosting logins outside company domains"
      enabled               = true
      mode                  = "WARN"
      title                 = "This is not a company account"
      subtext               = "Company code belongs in company accounts."
      terminate_button_text = "Sign out"
      continue_button_text  = "Continue anyway" # required for WARN only

      criteria = {
        app_types       = { matches = ["GITHUB"] }
        domain_scope    = "NON_COMPANY_DOMAINS"
        employee_groups = { matches = ["Contractors"], action = "EXCLUDE" }
      }
    },
  ]
}
```

### Required

- `rules` (Attributes List) The control's rules, in evaluation order: the first rule that matches wins, so the order of this list is part of your configuration.

<a id="nestedatt--rules"></a>
### Nested Schema for `rules`

Required:

- `criteria` (Attributes) Restricts the rule to apply only under these conditions. (see [below for nested schema](#nestedatt--rules--criteria))
- `enabled` (Boolean) Whether the rule is active.
- `mode` (String) What happens when the rule matches. One of `OFF`, `MONITOR`, `WARN` or `BLOCK`.
- `name` (String) A short name to help you recognise the rule. Not required to be unique. At most 250 characters.

Optional:

- `continue_button_text` (String) Text of the button that lets the user continue past the warning. Between 1 and 75 characters. Must not contain `&`, `<` or `>`, which the API stores HTML-escaped.
- `key` (String) A stable identifier for this rule, chosen by you and unique within the control. It is never sent to the API; the provider uses it to remember which server-side rule this configuration block corresponds to.

~> Set this on every rule. Rule names are not unique — the console generates names from a template, so duplicates are common — and without `key` the provider has to match rules by position. Reordering positionally matched rules keeps the server-side rule identifiers but moves them onto different rules. Nothing in Push refers to a rule identifier, so the tenant behaves the same either way; set a key if your own tooling reads the identifiers the API returns.
- `subtext` (String) Message of the page shown to the user. Markdown is supported. Between 1 and 1000 characters.
- `terminate_button_text` (String) Text of the button that ends the session, signing the user out of the app. Between 1 and 75 characters. Must not contain `&`, `<` or `>`, which the API stores HTML-escaped.
- `title` (String) Heading of the page shown to the user. Between 1 and 75 characters. Must not contain `&`, `<` or `>`, which the API stores HTML-escaped.

Read-Only:

- `id` (String) The rule's server-assigned identifier.

### Nested Schema for `rules.criteria`

Required:

- `app_types` (Attributes) Match logins to these apps. `ANTHROPIC` and `ANTHROPIC_CLAUDE` are treated as one app, as are `OPENAI` and `OPENAI_CHATGPT`, so naming either covers both. (see [below for nested schema](#nestedatt--rules--criteria--app_types))
- `domain_scope` (String) Match by the domain of the email the user logs in with: `COMPANY_DOMAINS` matches an email on one of your company domains, `NON_COMPANY_DOMAINS` an email on any other domain, and `SPECIFIC_DOMAINS` the domains listed in `login_domains`. One of `COMPANY_DOMAINS`, `NON_COMPANY_DOMAINS` or `SPECIFIC_DOMAINS`.

Optional:

- `browser_types` (Attributes) Match by the browser in use, as the Push browser extension identifies it. (see [below for nested schema](#nestedatt--rules--criteria--browser_types))
- `employee_groups` (Attributes) Match employees by the groups they belong to. (see [below for nested schema](#nestedatt--rules--criteria--employee_groups))
- `employee_ids` (Attributes) Match specific employees by email address. The provider resolves addresses to the identifiers the API matches on, in both directions, so configuration never holds a UUID. (see [below for nested schema](#nestedatt--rules--criteria--employee_ids))
- `login_domains` (Attributes) The email domains to match. Required when `domain_scope` is `SPECIFIC_DOMAINS`, and must be omitted otherwise. A login matches when its email's domain is one of these exactly, so `example.com` does not match `user@mail.example.com`. With `action = "EXCLUDE"`, the rule matches every login whose email domain is not listed. The API stores domains in lowercase, so write them that way. (see [below for nested schema](#nestedatt--rules--criteria--login_domains))
- `login_types` (Attributes) Match by how the user logs in: `PASSWORD_LOGIN` with a username and password, `OIDC` or `FEDCM` through single sign-on over that protocol. A rule with this criterion, whatever its `action`, only matches at login; a rule without it also matches a session that is already signed in as it is used. (see [below for nested schema](#nestedatt--rules--criteria--login_types))
- `profile_scope` (String) Match by the profile in use on the browser. One of `ALL`, `COMPANY_DOMAIN` or `NON_COMPANY_DOMAIN`. Defaults to `ALL`.

## Import

With Terraform 1.14 or later, `terraform query -generate-config-out` writes
the resource and its import block for you, using the `pushsecurity_account_condition_enforcement` list
resource. Its page shows how.

Import the existing configuration before your first apply, so that the apply is
a no-op rather than a replacement of whatever is already live.

```terraform
import {
  to       = pushsecurity_account_condition_enforcement.this
  provider = pushsecurity
  id       = "default"
}
```

Terraform 1.12 and later also accept the resource's identity in place of `id`.
The value is ignored, as the identifier is:

```terraform
import {
  to       = pushsecurity_account_condition_enforcement.this
  provider = pushsecurity
  identity = { id = "default" }
}
```

Either way, let Terraform write the configuration:

```shell
terraform plan -generate-config-out=generated.tf
```

Move the generated resource into your configuration, then **remove the
`provider` argument from the import block** — Terraform only accepts it on
import blocks that generate configuration, and leaving it in place fails the
next plan. Then run `terraform apply` to record the import.

Two things to expect:

- Generated rules have `key = null`, because keys are provider-side only and
  cannot be recovered from the API. Fill them in while adopting the control;
  the first apply after doing so is a no-op on the API.
- The API can return configuration that it rejects on write, so an import can
  produce a zero-diff plan and still fail validation on a later apply. This
  provider checks the API's cross-field rules during plan, so such rules are
  reported against the offending attribute before anything is
  written. Fix them as part of adoption.
