# pushsecurity_employee_merge (Resource)

Merges an employee's other addresses — `.admin`, `.support`, a personal alias, an address from a previous domain — into the record that represents them, so that detections and controls see one person rather than several.

~> **Terraform does not undo a merge.** `terraform destroy`, or removing an address from `secondary_emails`, stops Terraform tracking the merge but leaves the records merged. An address that had accounts of its own can be split out again, as a new employee with a new identifier; an address that had none cannot. Treat this resource as append-only.

A merge leaves no record of itself, so what this resource asserts is that the addresses in `secondary_emails` **do not exist as separate employees**. That is what a merge leaves behind, and it is checked on every refresh: an address that comes back — recreated by an HR sync, or by somebody signing in with it — appears in `pending_merges` and the next apply merges it again.

## Example usage

```terraform
# One person, several addresses. The primary is the record that survives; the
# others stop existing as separate employees, so a detection on the .admin
# account is attributed to the person who owns it.
resource "pushsecurity_employee_merge" "ada_lovelace" {
  primary_email = "ada.lovelace@example.com"
  secondary_emails = [
    "ada.lovelace.admin@example.com",
    "ada.lovelace.support@example.com",
  ]
}

# Addresses the tenant does not hold are accepted and warned about: once an
# address has been merged it looks exactly like one that never existed, so a
# re-run after losing state is a no-op rather than an error.
```

## What this resource can and cannot know

A merge leaves no record. The API reports nothing about it afterwards:
`knownEmails` holds the distinct addresses of the accounts an employee owns, not
the employees that were merged into them. A merge moves the secondary's
accounts onto the primary, so a merged address appears there only if it had
accounts of its own. Nor does a successful response from the merge endpoint
confirm that anything was merged, so the provider checks each merge by reading
the secondary back and expecting it to be gone.

So the invariant this resource keeps is not "these records were merged" but
**these addresses are not separate employees**, which is observable, and is what
a merge achieves. Three consequences:

- Every merge is confirmed by reading the secondary back and requiring it to be
  gone. A `200` on its own is not treated as success.
- An address the tenant does not hold is a warning, not an error. After a merge
  that is exactly what it looks like — so this is also what a re-run after
  losing state looks like, and it does the right thing.
- An address that comes back, because an HR sync recreated it or somebody
  signed in with it, shows up in `pending_merges` on the next refresh and is
  merged again by the next apply.

## Terraform does not undo a merge

`terraform destroy`, and removing an address from `secondary_emails`, stop
Terraform tracking the merge and warn that the records stay merged.

How far a merge can be reversed depends on what the address had. An address
that had accounts of its own stays among the primary's known addresses, and can
be split out again, through the API's `/unmerge` endpoint or by Push support,
as a licensed employee with a new identifier, which needs a free licence seat:
the original record and its identifier do not come back. A placeholder
address, one that had no accounts, leaves nothing behind to split out.

Treat the resource as append-only, and review a plan that merges somebody new as
carefully as you would a deletion.

## Schema

### Required

- `primary_email` (String) The address of the employee everything else is merged into. This record survives the merge; the others do not.

Changing it replaces the resource, which merges the same addresses into somebody else. It does not move them back.
- `secondary_emails` (Set of String) The addresses to merge into `primary_email`. Addresses the tenant does not hold are accepted and reported as a warning: after a merge that is exactly what an address looks like, so it cannot be distinguished from a typo.

The API merges five at a time; longer lists are sent as several requests.

### Read-Only

- `pending_merges` (Set of String) The addresses from `secondary_emails` that currently exist as separate employees, and will be merged by the next apply. Empty once the merge has been performed, so a plan that shows an entry here is telling you an address has come back.
- `primary_employee_id` (String) The identifier of the surviving employee record.

## Import

```shell
# Import by the primary employee's email address. Which addresses were merged
# into that person is not recorded anywhere the API exposes, so the import
# adopts the primary only: write secondary_emails yourself, and the first apply
# is a no-op for the ones that are already merged.
terraform import pushsecurity_employee_merge.ada_lovelace ada.lovelace@example.com
```

An import adopts the primary only — which addresses were merged into somebody
is not recorded anywhere the API exposes, so it cannot be discovered. Write
`secondary_emails` to say what this person's addresses are; the first apply is a
no-op for the ones that are already merged.
