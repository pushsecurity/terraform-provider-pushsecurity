# pushsecurity_employee (Resource)

Manages an employee record and whether they hold a Push licence.

An address the tenant already holds is **adopted**: the resource takes over the attributes you set and leaves the rest alone. An address it does not hold is created, which needs `first_name` and `last_name` and consumes a licence — the API licenses new employees automatically. The one address that is neither adopted nor created is one the tenant does not hold and `licensed = false` describes: nothing is sent, `employee_id` stays null, and a warning says the block can be removed.

~> **Removing a licence destroys data.** It deletes the employee record, the employee's accounts, the findings raised against them and their browsers. So `licensed = false` needs `allow_unlicense = true` beside it, and `terraform destroy` never unlicenses anybody — it stops managing them and warns. Removing this resource from your configuration leaves the employee exactly as they are.

## Example usage

```terraform
# An address the tenant already holds is adopted: this grants a licence and
# leaves everything else — groups, names from the directory — alone.
resource "pushsecurity_employee" "ada_lovelace" {
  email    = "ada.lovelace@example.com"
  licensed = true
}

# An address the tenant does not hold is created, which needs a name. Creating
# an employee consumes a licence: the API licenses new employees automatically.
resource "pushsecurity_employee" "contractor" {
  email      = "sam.okafor@contractor.example.com"
  first_name = "Sam"
  last_name  = "Okafor"
}

# Removing a licence deletes the employee record, their accounts, the
# findings raised against them and their browsers, so it has to be asked for
# twice.
resource "pushsecurity_employee" "departed" {
  email           = "alex.ward@example.com"
  licensed        = false
  allow_unlicense = true
}
```

## Removing a licence is not the opposite of granting one

Granting a licence is ordinary and reversible. Removing one is neither: the API
deletes the employee record, every account Push holds for that employee,
every finding raised against them, and their browsers.

An ordinary Terraform resource reaches that two ways without anybody typing it —
`terraform destroy`, and a resource block deleted from a file — so this one does
not behave like an ordinary resource:

| What you do | What happens |
| --- | --- |
| `licensed = true` | The licence is granted |
| `licensed = false` | **Refused during plan**, unless `allow_unlicense = true` is set beside it |
| Remove the resource from your configuration | Terraform stops managing the employee. Nothing is unlicensed |
| `terraform destroy` | The same: a warning, and no change to the employee |
| `licensed = false` for an address the tenant does not hold | Nothing is sent. The resource is satisfied, with a null `employee_id`, and a warning says the block can be removed |

To decommission somebody, apply `licensed = false` with `allow_unlicense = true`
and read the warning it prints, then remove the resource. Doing it in that order
means the destructive step is a thing you asked for and reviewed, rather than a
side effect of tidying up a configuration.

The block does not have to be removed straight away. Unlicensing deletes the
employee record, so after that apply the address is no longer in the tenant.
The resource treats that as the state it asked for: a
refresh keeps it, with `employee_id` null, and later plans are empty rather than
proposing to create the employee only to unlicense them again. The same holds
for a block written for an address that was never there. While the block stays,
it still means what it says: an employee who reappears at that address, from a
directory sync for instance, is unlicensed again by the next apply.

## Do not manage an address that a merge rule will merge

An address merged into somebody else stops existing as an employee. If a
`pushsecurity_employee` resource still manages that address, the next plan proposes to
**create it again** — and a
[`pushsecurity_employee_merge_rule`](employee_merge_rule) will merge it again on the
apply after that, forever.

Manage the people, not their aliases. If you created aliases deliberately — to
seed a test tenant, say — remove those resources from the configuration once the
merge has happened.

## Schema

### Required

- `email` (String) The employee's primary email address, which is how this resource finds them, compared ignoring case. Changing it replaces the resource: it adopts or creates a different person, and leaves the previous one untouched. Changing only its case does not.

### Optional

- `allow_unlicense` (Boolean) Permits `licensed = false` to be applied. Without it, a configuration that would remove a licence fails during plan, naming what would be deleted.

It never causes anything on its own: it only unlocks a `licensed = false` you have already written.
- `first_name` (String) The employee's first name. Required when the address is not already in the tenant, because creating an employee needs one.
- `last_name` (String) The employee's last name. Required when the address is not already in the tenant.
- `licensed` (Boolean) Whether the employee holds a licence. Leave it unset to adopt whatever the tenant has without managing it.

Setting it to `false` deletes the employee record along with their accounts, findings and browsers, so it is refused unless `allow_unlicense` is also `true`. Once applied, the address is no longer in the tenant, and an address the tenant does not hold is left that way: the resource then holds no `employee_id`, plans nothing, and can be removed.

### Read-Only

- `employee_id` (String) The identifier the API holds for this employee. Null when there is no record to identify: an address `licensed = false` describes that the tenant does not hold, which is where unlicensing leaves an employee. After an apply that unlicenses, it is cleared by the next refresh.
- `groups` (Set of String) The groups the employee is in, as used by the `employee_groups` criterion. Read-only here: groups come from the tenant's directory integrations, and this provider does not overwrite them.

## Import

With Terraform 1.14 or later, `terraform query -generate-config-out` writes
the resources and their import blocks for the employees you filter it to,
using the `pushsecurity_employee` list resource. Its page shows how.

```shell
# Import by email address. The resource adopts the employee; nothing is
# licensed, unlicensed or changed until you write an attribute saying so.
terraform import pushsecurity_employee.ada_lovelace ada.lovelace@example.com
```

In Terraform 1.12 and later, an import block can name the employee by identity
instead. The address is compared ignoring case, and the resource takes it as
written:

```terraform
import {
  to       = pushsecurity_employee.ada_lovelace
  identity = { email = "ada.lovelace@example.com" }
}
```
